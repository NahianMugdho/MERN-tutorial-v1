🛡️ অ্যাডভান্সড ব্যাকেন্ড সিকিউরিটি

JWT পেজে একটাই টোকেন ছিল। আসল প্রজেক্টে এটা যথেষ্ট না — টোকেন চুরি হলে কী হবে? পাসওয়ার্ড লিক হলে? ব্রুট-ফোর্স হলে? এই পেজে সেগুলোর সমাধান কোডসহ আছে। এখানকার ফাইল-নামসহ কোডগুলো সরাসরি সিকিউর মিনি প্রজেক্টে ব্যবহার হয়েছে।

বিষয়কী সমস্যা সমাধান করে
Access + Refresh Tokenছোট মেয়াদি টোকেন → চুরি হলে ক্ষতি কম
Rotation + Revokeচুরি ধরা ও সেশন বাতিল
Redisদ্রুত স্টোর: সেশন, ব্ল্যাকলিস্ট, রেট-লিমিট, ক্যাশ
Rate Limitব্রুট-ফোর্স ও স্প্যাম ঠেকানো
Argon2পাসওয়ার্ড নিরাপদে হ্যাশ
2FA (TOTP)পাসওয়ার্ড জানলেও ঢুকতে না পারা
API Cacheদ্রুত রেসপন্স, ডাটাবেজের চাপ কম

১. Access Token vs Refresh Token

Access TokenRefresh Token
কাজপ্রতিটি API তে পরিচয় দেখানোনতুন access token আনা
মেয়াদছোট — ১৫ মিনিটলম্বা — ৭ দিন
কোথায় রাখবেফ্রন্টেন্ডের মেমরিতে (JS ভ্যারিয়েবল)httpOnly কুকি (JS পড়তে পারে না)
কোথায় যায়Authorization: Bearer ...শুধু /api/auth/refresh এ, ব্রাউজার নিজে পাঠায়
সার্ভারে স্টোরনা (stateless), শুধু revoke হলে ব্ল্যাকলিস্টহ্যাঁ — Redis এ jti, নইলে revoke করা যায় না
কেন দুটো? একটাই লম্বা টোকেন চুরি হলে ৭ দিন হ্যাকার ঢুকতে পারে। ছোট access token চুরি হলে ১৫ মিনিটেই অকেজো; আর লম্বা refresh token এমন জায়গায় (httpOnly কুকি) যেখানে XSS পৌঁছায় না এবং সার্ভার চাইলেই বাতিল করতে পারে।

২. Refresh Token Rotation ও Revoke

Rotation: প্রতিবার refresh করলে পুরনো refresh token বাতিল, নতুন একটা আসে। প্রতিটি refresh token একবারই চলে। Reuse detection: বাতিল টোকেন আবার এলে বোঝা যায় কেউ চুরি করেছে (আসল ইউজার বা চোর, একজন পুরনোটা ব্যবহার করছে) — তাই সেই ইউজারের সব সেশন বন্ধ করে নতুন করে লগইন করানো হয়।

Revoke তিন রকম:

ধরনকখনকীভাবে
একটি সেশনLogoutrefresh jti মোছো + access jti ব্ল্যাকলিস্ট
সব সেশন"সব ডিভাইস থেকে লগআউট", পাসওয়ার্ড বদল, চুরি সন্দেহrts:user সেটের সব jti মোছো
Access token এখনইঅ্যাকাউন্ট ব্যান/লগআউটbl:jti Redis এ, TTL = বাকি মেয়াদ

ফ্রন্টেন্ড: স্বয়ংক্রিয় refresh

⚠️ CORS এ credentials: true ও নির্দিষ্ট origin (* নয়) লাগবে। ক্রস-সাইট ডেপ্লয়ে কুকিতে sameSite:'none' + secure:true।

৩. Redis

Redis হলো মেমরিতে চলা অতি দ্রুত key-value ডাটাবেজ, key তে মেয়াদ (TTL) বসানো যায়। এখানে ৪ কাজে লাগছে: refresh সেশন, access ব্ল্যাকলিস্ট, রেট-লিমিট কাউন্টার, API ক্যাশ। TTL শেষে key নিজে মুছে যায় — ক্লিনআপ লাগে না।

৪. Rate Limit

একই ক্লায়েন্ট নির্দিষ্ট সময়ে কতবার রিকোয়েস্ট করতে পারবে তার সীমা। লগইনে পাসওয়ার্ড অনুমান (brute-force) ঠেকাতে সবচেয়ে জরুরি। কাউন্টার Redis এ রাখলে সার্ভার রিস্টার্ট বা একাধিক সার্ভারেও সীমা ঠিক থাকে। সীমা পেরোলে 429 Too Many Requests।

Vercel/প্রক্সির পেছনে চালালে app.set('trust proxy', 1) দাও, নইলে সবার IP এক দেখাবে।

৫. Argon2 দিয়ে পাসওয়ার্ড হ্যাশ

পাসওয়ার্ড কখনো সাধারণ টেক্সটে বা SHA/MD5 তে রাখবে না। Argon2id স্বয়ংক্রিয় salt দেয় এবং ইচ্ছাকৃতভাবে মেমরি ও সময় খরচ করায়, ফলে GPU দিয়ে ব্রুট-ফোর্স ব্যয়বহুল। বর্তমানে OWASP এর প্রথম সুপারিশ (bcrypt এর চেয়ে আধুনিক)।

৬. 2FA (TOTP — Google Authenticator)

পাসওয়ার্ড জানলেও ঢোকা যাবে না, ফোনের অ্যাপের ৬ ডিজিট কোডও লাগবে, যা প্রতি ৩০ সেকেন্ডে বদলায়। সার্ভার ও অ্যাপ একই secret থেকে সময় ধরে কোড হিসাব করে।

ধাপকী ঘটে
Setupসার্ভার secret বানায় → QR কোড দেখায় → ইউজার অ্যাপে স্ক্যান করে
Enableইউজার অ্যাপের কোড দেয় → ঠিক হলে 2FA চালু (আগে যাচাই না করে চালু করবে না)
Loginপাসওয়ার্ড ঠিক → tempToken (৫ মিনিট) → কোড দিলে তবেই access+refresh
প্রোডাকশনে DB তে secret সরাসরি না রেখে এনক্রিপ্ট করে রাখো, আর একবার-ব্যবহার্য ব্যাকআপ কোডও দাও (ফোন হারালে)।

৭. API Cache (Redis)

যে GET রেসপন্স বারবার একই থাকে সেটা ডাটাবেজ থেকে না এনে Redis থেকে দিলে কয়েক গুণ দ্রুত হয়। নিয়ম: GET কে cache, লেখার (POST/PUT/DELETE) সময় cache মুছো — নইলে পুরনো ডাটা দেখাবে। ব্যক্তিগত ডাটার key তে ইউজার আইডি রাখো, নইলে একজনের ডাটা আরেকজন পাবে।
